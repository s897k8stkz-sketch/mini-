# 挑战交付物审计器

## 这个技能解决什么问题

挑战平台下发的要求是一串**模糊模式**，例如：

```
*skill说明*,*.skill,*教学说明*,*demo*,*AI日志*
```

学生看着目录觉得"文件都在"，提交后却被判 `missing_artifacts`（核心交付物缺失，该项封顶 5 分）。
绝大多数失分不是没写，而是三类**静默失败**：

1. **0 字节文件**——文件存在、名字对，内容为空（PowerShell `> file`、编辑器崩溃、同步中断都会产生）；
2. **模式不对齐**——要求 `*skill说明*`，文件名写成 `技能说明.md`，人有意识"就是它"，机器判定为无；
3. **放错层级 / 混入垃圾**——文件在子目录里、临时文件 `~$xxx.docx`、占位文件 `新建文本文档.txt` 被一起提交。

本技能把"提交前肉眼核对"变成一条**可复跑的命令**，输出确定性的判定表。

## 何时使用

- 交付物写完了，准备点"提交"之前；
- 平台回执说交付物缺失，需要定位到底缺哪一项；
- 换机器/换目录后，需要确认文件搬迁没有丢内容。

## 何时不要用

- 需要判断**内容质量**（写得够不够好）——本技能只判"在不在、空不空"，不判好坏；质量评审请走评审流程。
- 需要上传或提交——本技能是只读的，不做任何写入平台的动作。

## 输入契约

| 参数 | 必填 | 说明 |
|------|------|------|
| `--dir` | ✅ | 待审计的交付物目录（绝对路径或相对路径） |
| `--spec` | ✅ | 平台要求清单原文，逗号分隔，支持 `*`/`?` 通配 |
| `--min-bytes` | ❌ | 认定"非空"的最小字节数，默认 1 |
| `--json` / `--md` | ❌ | 把完整报告落盘为 JSON / Markdown |

平台清单来源（三处任一）：挑战页面「交付物」字段、资料包 `challenge.json` 的
`deliverables` / `required_deliverables`、`get-challenge` 返回体。**直接原文粘贴**，不要手工改写模式。

## 输出契约

标准输出为 Markdown 判定表，退出码即结论：

- `0` → `ready: true`，可以提交；
- `1` → 存在 `MISSING` 或 `EMPTY`，**先整改再提交**；
- `2` → 用法错误（目录不存在等）。

JSON 报告字段：`ready`、`passed/required`、`requirements[]`（每项含 `verdict` 与 `matches[]`）、
`risks[]`、`inventory[]`（含每个文件的字节数）。

判定枚举（四项，互斥）：

| verdict | 含义 | 处理 |
|---------|------|------|
| `PASS` | 精确命中且有内容 | — |
| `PASS_FUZZY` | 仅子串命中（模式与文件名不完全一致） | 通常可用，但建议按模式改名对齐 |
| `EMPTY` | 有命中文件，但全部小于 `--min-bytes` | 补内容，最常见的是 0 字节 |
| `MISSING` | 无任何命中 | 新增文件，文件名必须含模式关键词 |

## 执行步骤

1. 拿到平台清单原文（不要凭记忆写）。
2. 运行：

```bash
python scripts/audit.py --dir "<交付物目录>" --spec "*skill说明*,*.skill,*教学说明*,*demo*,*AI日志*"
```

3. 读判定表：
   - 全 `PASS` → 可以提交；
   - 出现 `MISSING` → 看"整改清单"逐条补文件，**文件名必须包含该模式的关键词**；
   - 出现 `EMPTY` → 打开命中文件核实内容，0 字节一律重建（不要用 `>` 重定向写中文内容）。
4. 若 `risks[]` 有 `error` 级项（0 字节、不可读），先清掉再提交。
5. 整改后**重跑同一条命令**，直到退出码为 0。把两次输出都留档，作为"提交前自检"的证据。

## 示例（真实运行）

对一个只有 C1/C2 交付物的仓库根目录，用 C4 的清单审计：

```
$ python scripts/audit.py --dir repo --spec "*skill说明*,*.skill,*教学说明*,*demo*,*AI日志*"
结论：**NOT READY 不可提交**（0/5 项满足，共 12 个文件）
| 1 | `*skill说明*` | MISSING | — | — |
...
```

补齐 5 个文件后重跑：

```
结论：**READY 可以提交**（5/5 项满足，共 18 个文件）
```

## 限制（如实声明）

- 只做**模式级**匹配，不理解语义：把 `*demo*` 写成 `demo` 目录里的空文件仍会被判 `PASS`（仅当字节数 ≥ 阈值）。
- 不做文件类型校验：`*.skill` 只要存在就不判错，包内结构是否合法需另查（`.skill` 为 ZIP 容器，须含 `技能名/SKILL.md`）。
- 不联网、不调用平台接口，因此不能替代平台的 `check-deliverables`；它是**提交前的本地预检**，用来把平台的判罚提前暴露。
- 中文文件名不做 NFC/NFD 归一化，极端情况下全角/半角混用可能漏配（会以 `info` 级风险提示）。
